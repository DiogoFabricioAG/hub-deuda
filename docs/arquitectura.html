Hub de Deuda · documentación técnica

Arquitectura en tres infraestructuras

Todo el sistema corre en la nube de Microsoft del tenant UNI. El PC Windows simula el servidor on-premise de origen y sirve para desarrollar y desplegar. El VPS meowlab solo aloja un prototipo visual con datos sintéticos y hoy no está conectado al hub.

¿Power Platform puede correr en el VPS? No.

Power Apps, Power Automate y Power BI Service son SaaS de Microsoft: no tienen instalador para servidores propios. Sus apps y flujos se ejecutan en la nube de Microsoft, dentro del entorno ligado a la cuenta UNI. El VPS tampoco puede alojar el Self-hosted Integration Runtime, que solo existe para Windows; por eso va en el PC.

Qué corre dónde

Nube de Microsoft

SaaS/PaaS · tenant UNI · todo el sistema

  • Microsoft 365: sitio SharePoint IntegracionDeuda (Entradas, ConfigAreas, Plantillas, Reportes, Evidencias), Outlook y Teams.
  • Power Platform, entorno Developer, solución HubDeuda: flujos de copia, avisos y reporte; apps ConsultaDeuda y Mis observaciones.
  • Azure rg-hubdeuda-dev: Storage, Function App, Azure SQL HubDeuda, Data Factory, Key Vault, Application Insights y Entra ID.
  • Power BI Service: tablero Resumen, Integración y Calidad.

PC Windows 11 del usuario

On-premise simulado + estación de desarrollo

  • SQL Server Express localhost\SQLEXPRESS con BDOrigen.dbo.DeudaOrigen (3 deudas ficticias).
  • Self-hosted Integration Runtime: solo Windows, conexiones salientes.
  • Repositorio Git D:\hub-deuda-azure, CLIs de despliegue y Power BI Desktop.

VPS meowlab

Prototipo independiente · fuera de Azure

  • Caddy sirve meowlab.tech: /debt-hub/ → nginx hub-deuda-staging.
  • /debt-hub/api/* → hub-deuda-api-v4 (Python + SQLite, datos sintéticos).
  • También aloja otros sitios y el agente Hermes. Hoy no está conectado a Azure ni a Power Platform.

Limitantes y por qué

Power Platform no se instala en el VPS

Por qué: Power Apps y Power Automate son SaaS. Microsoft los ejecuta en su nube y cada app o flujo pertenece a un entorno del tenant UNI.

Consecuencia: todo lo de Power Platform vive en la nube de Microsoft. El VPS no participa en el hub.

Power BI Service tampoco

Por qué: también es SaaS. Publicar en un workspace compartido requiere Pro, PPU o Fabric; con licencia gratuita solo existe «Mi área de trabajo».

Consecuencia: el modelo se hace en Power BI Desktop (PC) y se publica en «Mi área de trabajo» para demostrar, no para compartir.

El SHIR no puede ir en el VPS

Por qué: el Self-hosted Integration Runtime solo existe para Windows y el VPS es Ubuntu.

Consecuencia: el SHIR se instala en el PC, junto a SQL Server Express.

El PC debe estar encendido en las cargas horarias

Por qué: el SHIR y BDOrigen viven en el PC; si se apaga o suspende, ADF no puede leer el origen.

Consecuencia: la carga de esa hora falla sin dañar nada. La última base válida sigue publicada y vEstadoFuentes muestra el corte atrasado (pruebas T13/T14).

El SQL local nunca se expone a Internet

Por qué: el SHIR inicia conexiones salientes (HTTPS 443 hacia ADF y 1433 hacia Azure SQL); no se abren puertos de entrada en el PC.

Consecuencia: la red del PC debe permitir la salida por 443 y 1433.

Developer Plan: solo el dueño usa lo Premium

Por qué: el plan gratuito es individual y los conectores SQL Server y Azure Blob son Premium.

Consecuencia: alcanza para construir y presentar. Cada integrante que quiera usar las apps necesita su propio Developer Plan o una licencia.

Azure for Students limita regiones y presupuesto

Por qué: la suscripción tiene una política de regiones permitidas y un crédito de unos USD 100.

Consecuencia: se despliega en una región permitida, con alertas de presupuesto. Al terminar el curso se apagan los disparadores y se elimina rg-hubdeuda-dev.

El VPS no está conectado al hub

Por qué: es un prototipo de demostración con datos sintéticos, fuera del tenant UNI.

Opción futura (no planificada): consumir en solo lectura una API o vistas del hub en Azure, con autenticación propia y permisos mínimos. No se implementa ahora.
